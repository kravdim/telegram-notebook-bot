## Итоговый вердикт

Проект остаётся сильным **release candidate** и заметно превосходит обычный
pet-project по эксплуатационной зрелости. Все десять конкретных замечаний
предыдущего аудита либо закрыты, либо существенно уменьшены. Production
работает, схема не расходится с ORM, текущие reminder/backup SLO зелёные,
изоляция пользовательских данных подтверждена отдельным боевым тестом.

Однако называть продукт образцово-показательным пока рано. Новый полный live
gate дал **81/82**, а не 82/82. Причина оказалась не утечкой чужих данных, а
реальным дефектом latency/backpressure: необязательная компрессия истории
удерживала пользовательский lock 85 секунд и задержала следующий, полностью
детерминированный ответ на 72 секунды.

Кроме этого, persisted interaction state ещё не образует завершённую надёжную
state machine: старые generic callback-кнопки могут воздействовать на новую
voice/memoir-сессию, а несколько workflows удаляют состояние до того, как
полезный результат надёжно сохранён.

**P0 не обнаружено. Перед публичной демонстрацией как эталонного проекта нужно
закрыть три P1 ниже и повторить единый 82/82 gate с искусственными provider
timeout.** После этого оставшиеся P2 можно показывать как честный engineering
backlog.

## Подтверждение исправлений предыдущего аудита

### Закрыто корректно

1. **ORM/schema drift.** Partial unique index
   `uq_tasks_one_open_frog_per_user` объявлен в модели. CI и production
   `alembic check` зелёные.
2. **Recurrence/reminder.** Следующее occurrence вычисляется один раз, reminder
   сохраняет исходное смещение и при пропущенном окне ставится немедленно, но
   не позже due time.
3. **Interaction CAS.** PostgreSQL claim/transition/clear/consume используют
   expected type, row lock и advisory lock для создания пустого slot.
4. **Groq preflight.** `groq_api_key` передаётся в общий runtime validator.
5. **Privacy rollback.** При обычной DB-ошибке исходный whitelist
   восстанавливается.
6. **Delivery fencing.** Lease продлевается после каждой принятой Telegram
   части, progress и финальный status привязаны к token.
7. **Backup catch-up/SLO.** Есть persisted daily slot, catch-up и проверка
   существования архива, размера и sidecar.
8. **Повторные callbacks.** Task/frog/reminder completion возвращают
   фактический закрытый статус.
9. **p95.** Используется nearest-rank через `ceil`.
10. **Документирование capacity.** В README зафиксирован наблюдавшийся RSS и
    рекомендован запас RAM для local Whisper.

Это не косметические правки: большая часть прошлого reliability backlog
реально закрыта и покрыта regression tests.

## Что в проекте особенно хорошо

- Production fail-fast проверяет config и migration revision до старта.
- PostgreSQL advisory singleton исключает второй polling/scheduler runtime.
- Напоминания не зависят от доступности LLM.
- Task completion собран в один атомарный workflow с row lock и продолжением
  recurrence.
- Digest/memoir delivery имеет durable multipart ledger и documented
  at-least-once semantics.
- Backup и recovery разделены по credentials и полномочиям.
- User deletion имеет dry-run, точную confirmation phrase, singleton lease и

- Боевой runner использует выделенного пользователя, Run ID, pre-cleanup и

- Prompt/tool output не принимается на доверии: есть typed intents,
  `extra="forbid"`, sanitization и forced-tool retry для мутаций.
- Документация честно различает saved provider response contract и реальную
  online intent accuracy.

## P1 — исправить до заявления «образцово-показательный»

### 1. Компрессия истории блокирует следующий запрос пользователя

**Подтверждено в production live E2E.**

После отправки ответа handler синхронно вызывает `_compress()` внутри
per-user lock:

- `bot/handlers/messages.py:720-722` — compression ожидается до завершения
  текущего pipeline;
- `bot/handlers/messages.py:766-791` — summarization вызывает
  `llm_client.chat()` напрямую, минуя `LLMQueue` и `PRIORITY_SUMMARIZE`;
- `bot/handlers/messages.py:163-179` — lock охватывает весь pipeline, включая
  post-response compression и `_finish_request()`;
- `bot/llm/client.py:57-75` — OpenAI client создаётся с SDK retries по
  умолчанию;
- `bot/llm/client.py:140-175` — поверх них реализован ещё один собственный
  retry loop.

Production timeline:

```text
12:03:42  пользователь уже получил ответ на O1
12:04:02  SDK retry
12:04:23  SDK retry
12:04:44  application retry 1/2 после timeout
12:05:04  summarization завершилась
           update durations: 85,5 с и 72,9 с
```

Из-за удерживаемого lock следующий O2, который должен пройти локальный regex
guard без LLM, не мог начать обработку. Это и дало 81/82.

Дополнительный риск: если compression снова падает, история остаётся выше
threshold и каждый последующий запрос повторяет дорогой post-response вызов.

Что сделать:

1. Не держать пользовательский lock ради необязательной компрессии.
2. Самый надёжный вариант — детерминированно ограничивать историю recent
   window без LLM. Если summary нужен, выполнять его отдельным background
   worker с коротким total deadline и version/CAS истории, чтобы старое summary
   не затёрло новые сообщения.
3. Не пускать summarization в единственный intent-worker: низкий priority не
   помогает после начала долгого запроса, потому что работа не preemptive.
4. Выбрать один слой retry. Если retries контролирует приложение, создавать
   `AsyncOpenAI(..., max_retries=0)`.
5. Ограничивать весь provider chain одним total deadline, а не timeout каждой
   вложенной попытки.
6. Добавить метрики `request_end_to_end`, `user_lock_wait`, `compression_time`
   и счётчик provider attempts.

Обязательный regression test: history выше threshold, summarizer зависает,
первый ответ уже отправлен, а второй deterministic запрос получает ответ за
заданный SLO и не ждёт summarizer.

### 2. Старые callback-кнопки не привязаны к конкретной interaction-сессии

Voice-кнопки имеют глобальные payload `voice_confirm`, `voice_edit`,
`voice_cancel` (`bot/handlers/voice.py:177-180`). Callback сначала предпочитает
process-local `_pending_transcripts`, а затем читает **текущий** DB state,
не проверяя `callback.message.message_id` или session nonce
(`bot/handlers/voice.py:190-215`). Cancel также очищает текущий voice state без
идентификации исходной сессии (`bot/handlers/voice.py:241-248`).

Воспроизводимый сценарий по контракту кода:

1. voice A создаёт кнопку A;
2. через 30 минут state A истекает;
3. voice B создаёт новый `voice_confirm` и кладёт transcript B в тот же cache;
4. пользователь нажимает старую кнопку A;
5. старый callback подтверждает или отменяет **voice B**.

После рестарта риск выше: process-local cache пуст, поэтому любая старая
generic-кнопка берёт текущий persisted state.

Та же проблема у `memoir_skip`: callback data всегда `memoir_skip`, а handler
не сверяет message ID и может старой кнопкой удалить state нового вопроса
(`bot/scheduler/memoir.py:25`, `bot/handlers/callbacks.py:29-40`).

Что сделать:

- выдавать каждой сессии компактный nonce и включать его в callback data;
- хранить nonce и Telegram message ID в PostgreSQL payload;
- при confirm/edit/cancel/skip сверять user, expected type, nonce и message ID;
- clear/transition выполнять compare-and-set не только по type, но и по
  session token;
- process-local dict/set использовать только как cache после проверки БД, а не
  как более приоритетный источник истины;
- добавить tests `A expires → B starts → old A confirm/edit/cancel/skip` и тот
  же сценарий после simulated restart.

### 3. Workflow state удаляется до успешного durable side effect

Persisted state переживает restart, но несколько handlers уничтожают его до
того, как полезное действие завершено:

- project completion state consume происходит до `dispatch()`
  (`bot/handlers/messages.py:320-330`);
- memoir state очищается до атомарной записи memoir + diary
  (`bot/handlers/messages.py:438-443`);
- chronometry state и in-memory marker очищаются до LLM/DB обработки
  (`bot/handlers/messages.py:468-475`);
- voice state очищается до исполнения подтверждённого текста
  (`bot/handlers/voice.py:195-215`).

Если БД или provider падает после clear/consume, пользователь получает ошибку,
но retry уже не имеет исходного контекста. Для memoir это может означать
потерю явно отправленной записи; для voice — потерю подтверждённого transcript;
для project completion — потерю шага уточнения.

Что сделать:

- ввести lifecycle `pending → processing → completed/failed` с session token;
- DB-only side effect и завершение state выполнять в одной транзакции;
- external-provider этапы делать retry-safe: claim processing lease, сохранять
  input, после durable write атомарно завершать state;
- при recoverable failure сохранять возможность повторить действие или явно
  вернуть кнопку retry;
- не использовать destructive consume как первый шаг workflow;
- протестировать сбой в каждой точке между claim, provider, domain commit и
  state completion.

## P2 — важные задачи следующего этапа

### 4. Application layer пока является совместимым фасадом, а не фактической границей

Направление правильное, но архитектурная документация описывает целевое
состояние несколько увереннее, чем реализовано:

- `dispatch()` строит typed intent и запускает command bus, но сразу возвращает
  только `result.text`;
- Telegram handler снова разбирает legacy prefixes `CONFIRM_DELETE:`,
  `CHOOSE_DELETE:`, `PROJECT_CREATED:` и `CONFIRM_PROJECT_COMPLETE:`;
- все bus handlers ведут в общий `_execute_registered_intent`, затем в
  `_COMMAND_EXECUTORS`, затем обратно в private business functions
  `llm/dispatcher.py`;
- `llm/dispatcher.py` всё ещё содержит около 1080 строк parsing, validation,
  domain orchestration и presentation protocol.

То есть `CommandResult.kind/payload` существует, но основной runtime-контур
его теряет и повторно декодирует строку.

Следующий архитектурный шаг:

- возвращать `CommandResult` до Telegram adapter без round-trip через sentinel
  strings;
- перенести use cases из `llm/dispatcher.py` в provider-neutral application
  services;
- оставить dispatcher только адаптером raw provider payload → typed intent;
- регистрировать отдельный typed handler на каждый intent;
- запретить application/domain слоям возвращать Telegram presentation
  protocol.

Это не текущий функциональный blocker, но опытный reviewer сразу заметит
несоответствие diagram и runtime dependency direction.

### 5. Coverage floor слишком низок для заявленного уровня надёжности

Общий coverage 45,01% формально выше floor 42%, но наиболее рискованные модули
покрыты слабо:

| Модуль | Coverage |
|---|---:|
| `db/crud/interaction_states.py` | 16% локально |
| `scheduler/backup.py` | 19% |
| `services/delivery.py` | 29% |
| `llm/dispatcher.py` | 35% |
| `main.py` | 18% |
| `application/interactions.py` | 48% |

Часть PostgreSQL-веток повышает показатель в CI, но новый live-дефект как раз
находился в непроверенной orchestration-ветке compression + lock + timeout.

Рекомендация: не гнаться сразу за общими 90%. Сначала ввести branch-oriented
tests для critical workflows и поднять project floor поэтапно до 60–70%, с
отдельными минимальными порогами для interaction, delivery, backup и command
execution.

### 6. Privacy deletion не crash-atomic между YAML и PostgreSQL

Исправление прошлого аудита корректно компенсирует обычное Python/DB
исключение. Но process kill, power loss или `SIGKILL` между строками изменения
whitelist и DB commit оставят пользователя удалённым из доступа, а его данные
— в БД. Это неизбежно без durable operation journal, потому что YAML и
PostgreSQL не участвуют в общей транзакции.

Документация не должна называть весь cross-system workflow атомарным. Нужен
persisted deletion operation с фазами, restart reconciliation и idempotent
resume либо явно документированный operator recovery command.

### 7. `/status` проверяет формат checksum sidecar, но не checksum архива

`backup_artifact_status()` сверяет existence, size, имя и синтаксис 64 hex
символов, но не вычисляет SHA-256 архива. Regression test специально принимает
sidecar из 64 нулей как `ok`.

Это допустимый performance trade-off для частого health check, но тогда
`artifact=ok` означает «marker/size/sidecar structurally valid», а не
«checksum agree». Для эталонности:

- хранить в marker verified digest и периодически считать hash отдельным job;
- либо переименовать status/documentation так, чтобы не обещать криптографическую
  проверку на каждом `/status`;
- recovery drill оставить обязательной полной проверкой.

### 8. Delivery failure bookkeeping не полностью fenced

Успешный progress и completion fenced token-ом. Но exception path обновляет
`DeliveryPart` по `part.id` без проверки текущего lease/token. Если lease истёк
во время Telegram call и другой worker уже продолжил batch, старый worker может
увеличить attempts и записать `last_error` в часть, которую новый worker уже
доставил. Batch update fenced, part update — нет.

Нужно обновлять part через join/exists к batch с текущим token либо включить
owner token в part progress contract. Риск невысок для одного production
runtime, но код заявляет корректность при concurrent sender и должен довести
её до конца.

### 9. Chronometry fallback может создать дубль при частичном успехе

`create_time_entry()` делает собственный commit. Затем handler отдельно
обновляет `chronometry_last_asked`. Если запись уже committed, а update settings
падает, общий `except` создаёт ещё одну fallback entry с тем же текстом.

Нужен один transaction boundary для entry + user marker или idempotency key
occurrence/message ID. CRUD-функции с внутренними commit затрудняют составные
use cases; предпочтительнее flush по умолчанию внутри application workflow и
commit на его границе.

### 10. Release documentation требует финальной полировки

- `CHANGELOG.md` не отражает фундаментальный reliability/application package
  commit `6b1acad`; сведения есть только в session context/remediation.
- В repository нет release tags, а `pyproject.toml` остаётся на `0.1.0`.
- `docs/ARCHITECTURE.md` следует явно пометить текущий command bus как
  transitional compatibility layer до удаления string protocols.
- Release checklist должен добавить forced-timeout/backpressure test и stale
  callback test, а не только happy-path 82/82.

Для внутреннего сервиса version `0.1.0` допустима, но для образцовой публичной
демонстрации нужны reproducible tag, release notes и явная матрица evidence.

## UX-оценка

### Сильные стороны

- Пользователь может говорить естественно, с опечатками, смешанным языком и
  несколькими намерениями.
- Опасные удаления требуют подтверждения.
- Голос показывается текстом до исполнения.
- Ошибочные даты, пустые команды и непонятные аргументы получают понятные
  ответы.
- Длинные ответы корректно дробятся под лимит Telegram.
- Реальное напоминание, snooze и повторные task callbacks работают.
- Отказ на запрос чужих данных короткий и правильный.

### Что ухудшает ощущение продукта

- После уже показанного ответа бот может молча удерживать следующий запрос
  больше минуты из-за внутренней housekeeping-операции.
- Старые кнопки визуально остаются активными и не умеют сказать «эта сессия
  устарела» на основе session identity.
- При provider/DB failure многошаговый диалог иногда исчезает вместо понятного
  retry.
- Нет явного пользовательского сообщения «запрос в очереди» при долгом
  ожидании per-user lock/provider.

Для планировщика доверие строится не только на правильном конечном результате,
но и на предсказуемой реакции. Минутное молчание после простого локального
запроса воспринимается как потеря сообщения.

## Вопросы разработчику

1. Какой целевой end-to-end SLO для обычного сообщения и для deterministic
   intent? Сейчас есть provider timeout, но нет пользовательского total SLO.
2. Зачем одновременно используются SDK retries и собственный retry loop?
3. Нужна ли LLM-компрессия вообще при небольшом allowlisted product, или
   deterministic recent-window будет надёжнее и дешевле?
4. Считается ли старый callback валидным после появления новой сессии того же
   типа? Если нет, где его session identity?
5. Какое гарантированное поведение при падении между state consume и domain
   commit?
6. Application layer задуман как законченная граница или как первый
   transitional этап? Документация должна отвечать так же, как код.
7. Какой coverage/branch coverage считается release target именно для
   reliability-модулей?
8. Как оператор возобновляет privacy deletion после process crash между YAML и
   PostgreSQL?
9. Какой статус должен показывать `/status`: наличие sidecar или реально
   подтверждённую целостность backup?
10. Когда появятся semantic version, tag и release notes для демонстрируемой
    версии?

## Release criteria для статуса «образцово-показательный»

- единый полный live gate: 82/82, не сумма раздельных прогонов;
- forced summarizer timeout не задерживает следующий deterministic запрос;
- total end-to-end latency имеет измеряемый SLO;
- старые voice/memoir callbacks не могут менять новую сессию;
- failure injection не теряет memoir/voice/project/chronometry context;
- production Alembic check и SLO остаются зелёными;
- critical workflow tests проходят с PostgreSQL;
- documentation описывает фактические, а не целевые dependency boundaries;
- релиз имеет version/tag и воспроизводимый evidence bundle.

## Финальная оценка

DailyPlanner уже не выглядит как проект, который серьёзные разработчики
«засмеют». Напротив, backup/recovery, CI, live E2E, migration discipline,
privacy workflow и эксплуатационный runbook производят сильное впечатление.

Главное сейчас — не испортить это впечатление преждевременным словом
«эталон». Боевой тест нашёл именно тот класс дефекта, ради которого нужен
настоящий beta-test: все отдельные функции правильны, но необязательная
внутренняя операция блокирует следующий пользовательский запрос. После
устранения P1 и повторного 82/82 у проекта будут очень убедительные основания
называться образцово-показательным release candidate.
