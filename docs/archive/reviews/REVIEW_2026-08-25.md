## Оставшиеся дефекты высокого приоритета

### 1. ORM metadata расходится с фактической схемой БД

Команда `alembic check` обнаруживает новую операцию:

```text
remove_index uq_tasks_one_open_frog_per_user
```

Миграция `4c9f17a8b2d1_reliability_foundation.py:142` создаёт уникальный partial
index, не позволяющий иметь две открытые лягушки.

ORM-модель в `bot/db/models.py:147` содержит только обычный неуникальный
`idx_tasks_frog`.

Сейчас production-защита работает, потому что индекс существует в БД. При
следующей autogenerate-миграции Alembic предложит удалить полезное ограничение.

Что сделать:

- объявить `uq_tasks_one_open_frog_per_user` в `Task.__table_args__`;
- добавить `alembic check` в CI после `alembic upgrade head`;
- считать любое schema drift падением release gate.

### 2. Следующее напоминание повторяющейся задачи может оказаться позже задачи

Дата следующей задачи и дата следующего напоминания вычисляются независимо в
`bot/services/tasks.py:76`.

Подтверждённый пример:

```text
сейчас:                 25.08 08:50
следующая задача:       25.08 09:00
следующее напоминание:  26.08 08:45
```

Так происходит, если просроченную ежедневную задачу завершить между временем
следующего напоминания и временем самой задачи. Задача назначается на сегодня,
а её reminder перескакивает на завтра.

Нужно вычислять один `next_at`, а напоминание получать из исходного смещения
относительно due time. Если время напоминания уже прошло, следует явно выбрать
продуктовую политику: отправить сейчас, пропустить для этого occurrence либо
перенести саму задачу. Нельзя связывать сегодняшнюю задачу с завтрашним
reminder.

### 3. Interaction state всё ещё имеет два источника истины и конфликты режимов

Мемуарник исправлен, но закрытие проекта всё ещё хранит дополнительный
бессрочный in-memory-флаг в `bot/handlers/messages.py:111`.

DB-state истекает через 30 минут, однако fallback остаётся в памяти. Следующее
сообщение спустя несколько часов может быть принято за название закрываемого
проекта (`bot/handlers/messages.py:137`).

Кроме того, на пользователя предусмотрена ровно одна строка interaction state:
`bot/db/models.py:162`. `set_state()` безусловно заменяет существующий тип:
`bot/db/crud/interaction_states.py:26`.

Мемуарник не проверяет занятость состояния и способен заменить
`voice_confirm`, `voice_edit` или ожидание названия проекта:
`bot/scheduler/memoir.py:46`.

Что сделать:

- убрать `_pending_project_completion` либо дать ему тот же timestamp/TTL;
- сделать PostgreSQL единственным источником истины;
- ввести compare-and-set: scheduler не заменяет активный пользовательский
  workflow;
- не отмечать memoir как отправленный, если состояние ответа сохранить не
  удалось;
- добавить тесты пересечений `voice ↔ memoir ↔ chronometry ↔ project completion`.

### 4. Документированный Groq STT всегда отклоняется preflight

`validate_runtime_config()` поддерживает `groq`, но
`Settings.runtime_config_errors()` не передаёт `groq_api_key` в словарь
provider keys: `bot/config.py:187`.

Дефект отдельно воспроизведён с валидным Groq key:

```text
['API key is missing for STT provider: groq']
```

Режим, заявленный в README и `config.yaml.example`, запустить нельзя.

Исправление:

```python
"groq": self.groq_api_key
```

Нужен тест именно через `Settings.runtime_config_errors()`, а не только прямой
вызов вспомогательного валидатора.

## Замечания среднего приоритета

### Privacy deletion не атомарен между файлом и PostgreSQL

Удаление атомарно внутри PostgreSQL, а whitelist-файл изменяется до DB commit:
`scripts/delete_user_data.py:57`. При ошибке БД пользователь останется в
таблицах, но уже исчезнет из whitelist.

Нужен rollback конфигурации либо двухфазный workflow с явно проверяемым
состоянием.

### Delivery lease имеет неполную защиту от долгой отправки

Outbox lease не продлевается во время отправки. После 300 секунд второй worker
может забрать batch. Первый при потере lease всё равно возвращает
`completed=True`: `bot/services/delivery.py:94`.

Для текущих небольших рассылок риск низок, однако следует:

- продлевать lease между частями;
- проверять lease token при фиксации каждой части;
- возвращать `completed=True` только если финальный update действительно
  изменил строку batch.

### Backup SLO не проверяет сам backup

`bot/observability.py:155` проверяет только возраст DB-marker. `/status` может
показать свежий backup после удаления или повреждения файла/checksum.

Следует проверять существование указанного архива, sidecar и хотя бы совпадение
имени/размера. Полный checksum можно оставить recovery job.

### Нет catch-up backup после простоя

Maintenance loop в `bot/main.py:285` запускается раз в час и создаёт backup
только при совпадении `now.hour` с `backup_hour`. Если приложение не работало в
этот час, следующий backup появится только через сутки.

Нужен persisted daily slot и catch-up после запуска, аналогично другим
scheduler-маркерам.

### Повторный callback сообщает неточный результат

Handlers проверяют наличие `completion.task`, но не `completion.completed`.
Старый callback уже выполненной или отменённой задачи может снова показать
«задача выполнена», хотя новая транзакция ничего не изменила.

Следует отвечать «задача уже закрыта» и показывать её фактический статус.

### Расчёт p95 занижает latency на малых выборках

В `bot/observability.py:113` индекс вычисляется как
`int(len * 0.95) - 1`. Для двух samples выбирается минимальное значение вместо
максимального. Следует использовать nearest-rank с `ceil`.

## Тестовая стратегия

Боевой gate стал намного лучше:

- уникальный Run ID;
- выделенный аккаунт;
- pre-cleanup;
- обязательный teardown;
- строгий итог `82/82`;
- N3 действительно требует подтверждение удаления;
- voice-сценарии ожидают появления кнопок.

Однако `utterance_contract_accuracy=1.000` всё ещё не оценивает распознавание
utterance. Поле `utterance` из fixture скриптом не используется; проверяется
только заранее сохранённый tool-call: `scripts/evaluate_llm_contracts.py:35`.
Документация теперь корректно называет это saved provider response contract,
но метрику нельзя трактовать как model intent accuracy.

Coverage 43.37% проходит установленный порог, однако критические модули покрыты
неравномерно:

- `services/tasks.py` — 36%;
- `services/delivery.py` — 33%;
- `scheduler/backup.py` — 15%;
- `dispatcher.py` — 33%.

Рекомендуется поднимать не произвольную общую цифру, а risk-weighted coverage
именно этих контрактов.

## Архитектурная рекомендация

Главный оставшийся технический долг — размеры и ответственность трёх файлов:

- `messages.py` — 1450 строк;
- `commands.py` — 1226 строк;
- `dispatcher.py` — 1012 строк.

В `messages.py` фактически появился второй rule-based intent engine из 25
helper-функций и большого набора regex. Он повышает детерминированность, но
частично дублирует LLM contracts и dispatcher. При дальнейшем развитии это
может привести к противоречивым правилам и переобучению на beta-сценарии.

Следующий архитектурный этап должен выделить:

- `IntentNormalizer`;
- typed deterministic intents;
- `InteractionService`;
- Telegram adapters;
- единый application command bus.

Это не блокирует текущий релиз, но важно для дальнейшего развития без
накопления противоречивых эвристик.

## Финальный вердикт

Проект уже **можно показывать серьёзным разработчикам**. Теперь он производит
впечатление настоящего продукта с продуманной эксплуатацией, а не учебного
Telegram-бота.

Перед формулировкой «все известные проблемы закрыты» необходимо исправить
четыре верхних пункта:

1. schema drift;
2. recurrence/reminder mismatch;
3. interaction-state conflicts и бессрочный fallback;
4. Groq preflight.

После этого останутся в основном hardening и архитектурное упрощение.
