# ADR: владение доставкой и повторы команд

Статус: реализовано локально в remediation-ветке; не описание production v0.5.0.

## Доставка

Одночастные reminders используют собственную запись occurrence с lease token,
lease expiry, next_attempt_at и числом попыток. Main loop и sweep вызывают один
claim/send/ack сервис; сетевой send выполняется без открытой DB-транзакции.
Weekly review использует существующий multipart DeliveryBatch, чтобы после сбоя
не начинать отправку длинного отчёта с первой части. Это разные единицы доставки,
а не два конкурирующих механизма для одной reminder-записи.

Telegram не предоставляет idempotency key для sendMessage. При успешном send и
потере ack возможен повтор уведомления. Lease предотвращает одновременную выдачу
одного occurrence двум отправителям, но не обеспечивает exactly-once Telegram.
После последней проверки lease остаётся окно in-flight send против отмены задачи.
Обещать отсутствие уведомления в этом окне нельзя. Domain acknowledgement защищён
токеном; новый владелец или отмена не должны быть перезаписаны старым отправителем.

Terminal/exhausted delivery — `failed`, а не пользовательская отмена. Владелец
видит ошибки через `/reminder_errors`; повтор разрешён только для незакрытой задачи.
Timezone фиксируется у серии. Catch-up пропускает прошлые повторения до ближайшего
будущего; изменение timezone профиля не переписывает существующие серии.

## Составные команды

ProcessedRequest сохраняет план до первого действия. Каждое действие фиксирует
domain effect и структурированный CommandResult одной PostgreSQL-транзакцией.
Совместимость legacy repositories обеспечена CommandSession: вложенный commit
становится flush только внутри явно установленной command_transaction; внешний
use case владеет durable commit. Внутренний rollback запрещает запись успеха.
Это переходный адаптер; замена неявного session context на явные typed UoW/ports
остаётся отдельной архитектурной работой, а не объявляется завершённой.

Результат сохраняется до отправки в Telegram. `/retry` восстанавливает тот же план
по request key с проверкой владельца. Завершённые действия читаются из журнала;
ошибочные выполняются снова. Декомпозиция проекта имеет отдельную journal phase,
связанную с уже созданным project; её задачи тоже фиксируются атомарно с результатом.
Повторные кнопки сериализуются пользовательским lock и проверкой состояния запроса.
Новый Telegram message с тем же текстом — отдельный запрос, не неявный retry.

Ротация удаляет только completed requests старше transient retention. Failed и
незавершённые планы сохраняются для retry; `/delete_data` удаляет их вместе с
данными владельца. Старые кнопки completed requests после retention не запускают
новые действия: callback сначала проверяет наличие сохранённого owner-scoped плана.

## Проверки и границы

Локальный PostgreSQL gate: 513 passed, 1 skipped, coverage 73.47% (04.09.2026).
Проверены rollback после legacy commit, error result без commit, replay после
сброса соединений, owner/position guard и swallowed rollback. Это не доказательство
полного live E2E, неизвестного результата сетевого COMMIT или совместимости старого
release с новой схемой: эти проверки пока остаются в плане.

Новые schema heads нельзя автоматически объявлять совместимыми с v0.5.0:
старый sender не понимает lease/failed. До deploy нужен отдельно доказанный
rollback-путь; downgrade migrations намеренно отказываются удалять незавершённые
планы и failed reminders. Не обходить эти ограничения ручным удалением данных.
