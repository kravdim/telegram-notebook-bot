# План исправления Telegram Notebook Bot

> Практический roadmap по устранению дефектов, найденных при аудите проекта.
>
> Статус документа: основной кодовый контур реализован 19.08.2026
> Приоритет проекта: надёжность данных и предсказуемость действий пользователя
> Правило выполнения: один этап — один или несколько небольших PR с обязательными тестами

## Статус реализации

В текущей рабочей копии реализован единый reminder-контур с миграцией legacy
данных, recurrence-idempotency и ограничением повторных доставок; per-user
pipeline и дедупликация сообщений; typed tool contract; строгая валидация дат;
безопасный Telegram renderer; DB-backed FSM и interaction states; исправления
хронометража, мемуарника, лягушек, проектов, поездок, вечернего разбора и дней
рождения; атомарные scheduler-slots; fail-closed доступ и privacy-safe LLM-логи;
Docker/systemd entrypoints, checksum-бэкапы и restore runbook.

Автоматическая проверка: `75 passed`, `compileall`, `git diff --check`, один
Alembic head `4c9f17a8b2d1`. Пункты ниже сохранены как подробный audit trail.
Проверка миграции на чистом и обновляемом реальном PostgreSQL, тестовое
восстановление backup и live Telegram smoke-test остаются релизными действиями:
они требуют отдельной тестовой инфраструктуры и внешних credentials.

## 1. Целевое состояние

После выполнения плана приложение должно гарантировать:

- задачи и напоминания не теряются и не создаются повторно;
- неоднозначные изменения не выполняются без уточнения пользователя;
- сообщения одного пользователя обрабатываются строго по порядку;
- рестарт приложения не ломает онбординг, кнопки и многошаговые диалоги;
- пользовательский и LLM-текст безопасно отображается в Telegram;
- фоновые задания не пропускаются и не дублируются;
- все заявленные возможности подтверждены автоматическими тестами;
- README, архитектурная документация и реальное поведение совпадают.

## 2. Правила работы с этим планом

Для каждого этапа разработчик должен:

1. Создать отдельную ветку.
2. Сначала добавить тест, воспроизводящий дефект.
3. Внести минимальное исправление.
4. Запустить весь набор проверок.
5. Проверить миграции на чистой БД и на копии существующей схемы, если этап меняет данные.
6. Обновить документацию в том же PR.
7. Отметить выполненные пункты чекбоксами только после прохождения критериев приёмки.

Рекомендуемые проверки перед каждым merge:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m compileall -q bot tests
.venv/bin/pytest -q
.venv/bin/alembic heads
```

После появления соответствующих инструментов добавить:

```bash
ruff check bot tests
mypy bot
```

Таблица `reminders` становится единственным источником доставки. Задача может быть связана с напоминанием через `task_id`, но scheduler не читает поля напоминания из `tasks`.

- [ ] Добавить `series_id` для повторяющихся напоминаний.
- [ ] Добавить `occurrence_at` или эквивалентный ключ occurrence.
- [ ] Добавить уникальный индекс `(series_id, occurrence_at)`.
- [ ] Мигрировать существующие `Task.remind_at` в связанные записи `Reminder`.
- [ ] При создании задачи с `remind_at` создавать `Task` и `Reminder` в одной транзакции.
- [ ] Перестать подтверждать «Напомню», пока запись `Reminder` не создана.
- [ ] Удалить `Task.remind_at` и `Task.remind_before_min` либо объявить их deprecated и прекратить использование.
- [ ] Сделать `mark_sent` идемпотентным.
- [ ] Не создавать следующее повторение повторно при нажатии «Сделано».
- [ ] Snooze должен переносить текущее occurrence, а не порождать новую серию.

- [ ] Выбрать один формат recurrence и использовать его в schema, БД и runtime.
- [ ] Предпочтительный вариант: RFC 5545 RRULE с отдельным валидатором.

### Обязательные тесты

- [ ] Задача с `remind_at` создаёт связанную запись `Reminder`.
- [ ] Напоминание доставляется ровно один раз при повторном запуске scheduler.

- [ ] Два scheduler-worker не забирают одно напоминание одновременно.
- [ ] Другой пользователь не может изменить напоминание по UUID.
- [ ] Невалидное repeat rule отклоняется до записи в БД.

### Критерии приёмки

- [ ] В приложении существует только один путь доставки напоминаний.
- [ ] Повторный вызов любого reminder-handler безопасен.
- [ ] В БД невозможно создать два одинаковых occurrence одной серии.

**Приоритет:** P0
**Основные файлы:** `bot/llm/queue.py`, `bot/handlers/messages.py`, `bot/main.py`, `bot/db/models.py`

### Целевой pipeline

```text
Telegram update
  -> дедупликация update_id
  -> очередь конкретного user_id

  -> транзакция
  -> сохранение результата
```

- [ ] Сохранять обработанные Telegram `update_id` и не исполнять их повторно.
- [ ] Сделать все изменяющие операции идемпотентными по `request_id`.
- [ ] Определить корректное поведение таймаута.
- [ ] При отмене ожидания отменять исполняемую операцию либо возвращать статус «выполняется».

## 18. Definition of Done проекта

Проект можно считать доведённым до целевого состояния, когда выполнены все условия:

- [ ] Нет известных сценариев потери задач или напоминаний.
- [ ] Нет известных сценариев дублирования повторяющихся напоминаний.
- [ ] Любая неоднозначная мутация требует выбора пользователя.
- [ ] Сообщения пользователя исполняются строго по порядку.
- [ ] Все mutation-handler идемпотентны.
- [ ] Рестарт не ломает активные многошаговые сценарии.
- [ ] Все пользовательские данные безопасно отображаются в Telegram.
- [ ] Фоновые задания имеют persistent idempotency markers.
- [ ] Backup автоматически создаётся и успешно восстанавливается.
- [ ] Production не запускается с небезопасной конфигурацией.
- [ ] Integration и end-to-end тесты входят в CI.
- [ ] README и архитектурная документация описывают только реально работающие функции.
